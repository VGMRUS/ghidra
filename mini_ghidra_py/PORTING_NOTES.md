# Notas de portado desde el source de Ghidra

## Port de este incremento: identificación de inicios de función x86

Se revisaron estas implementaciones y datos del repositorio:

- `Ghidra/Features/BytePatterns/src/main/java/ghidra/app/analyzers/FunctionStartAnalyzer.java`
- `Ghidra/Processors/x86/data/patterns/x86gcc_patterns.xml`
- `Ghidra/Processors/x86/data/patterns/x86-64gcc_patterns.xml`
- `Ghidra/Processors/x86/data/patterns/x86win_patterns.xml`

`FunctionStartAnalyzer` usa patrones de bytes, restricciones de código precedente/posterior y, por defecto, limita la búsqueda a bloques ejecutables. `function_starts.py` traslada esa idea a una tabla reducida de prólogos GCC/Windows comunes: el prólogo debe coincidir en una dirección de instrucción decodificada, estar en una sección ejecutable y cumplir un límite de flujo previo (inicio de sección, `ret`, salto incondicional, relleno o trap). También se trasladó el caso Windows `sub esp, imm8` después de un límite, exigiendo al menos dos instrucciones válidas para reducir falsos positivos. Las firmas genéricas de `sub rsp, ...` mantienen un requisito mayor de código alcanzable. Los candidatos aceptados aparecen en `patterns` y como origen de función en `functions`.

No se copió el motor de patrones de Ghidra: **no** se implementan `PatternDecisionTree`, el lenguaje completo de máscaras XML, los contextos de registros, las restricciones `after=...`, la gestión de bookmarks ni el `PseudoDisassembler` de Ghidra. La tabla Python es una selección explícita, no una traducción exhaustiva de los XML.

## Thunks y resolución de PLT

Este incremento también revisa `Ghidra/Features/Base/src/main/java/ghidra/app/cmd/function/CreateThunkFunctionCmd.java` (`getThunkedAddr`, `getSimpleFlow`) y `Ghidra/Features/Base/src/main/java/ghidra/app/plugin/core/function/FunctionAnalyzer.java`. Se reconocen saltos incondicionales directos con prólogo NOP/ENDBR opcional, y stubs ELF PLT que saltan por una ranura GOT. Para ELF se usa el orden de `pltgot_relocations` de LIEF y se valida el tamaño/stride de `.plt` o `.plt.sec` antes de crear nombres de stub; los layouts no habituales se ignoran.

El detector no emula el chequeo p-code de hasta ocho instrucciones ni el análisis de registros/efectos laterales de Ghidra. Tampoco resuelve thunks calculados por registros ni toda la variedad de referencias indirectas. La consola los muestra con `thunks`; el grafo del caller y las referencias pueden resolver los nombres PLT y las llamadas importadas no-return.

## Inicios de función Mach-O

Este subconjunto se basa en `Ghidra/Features/Base/src/main/java/ghidra/app/plugin/core/analysis/MachoFunctionStartsAnalyzer.java` y `Ghidra/Features/Base/src/main/java/ghidra/app/util/bin/format/macho/commands/FunctionStartsCommand.java`. Se leen los offsets ULEB128 de `LC_FUNCTION_STARTS` mediante LIEF, se suman a la dirección virtual del segmento `__TEXT` y se consideran después de recuperar las funciones evidentes, siguiendo la prioridad tardía de Ghidra. Solo se añaden como semillas si apuntan a una instrucción decodificada en bytes ejecutables, no son traps y todavía no pertenecen a un cuerpo recuperado. `info`, `functions` y `export-json` permiten ver los resultados.

Ghidra advierte que la lista puede contener falsos inicios; el port no replica `PseudoDisassembler.isValidSubroutine`, bookmarks ni el análisis de dyld caches divididas. Se limita a los comandos que LIEF exponga para la slice Mach-O elegida por el cargador (en binarios universales se prefiere x86-64); un punto que decodifica como instrucción aún puede ser un falso positivo.

## Inicios x64 de PE desde `.pdata`

Este subconjunto se basa en `Ghidra/Features/Base/src/main/java/ghidra/app/util/bin/format/pe/ExceptionDataDirectory.java` y `ImageRuntimeFunctionEntries_X86.java` (la tabla de 12 bytes `RUNTIME_FUNCTION` usada por PE x64). Se usan las entradas `exception_functions` de LIEF cuando están disponibles; si no, se lee el directorio EXCEPTION_TABLE desde las secciones PE y se decodifican las triples little-endian de `.pdata`. Se suman las RVA a la image base y se crean semillas en `BeginAddress`, salvo entradas encadenadas (`UNW_FLAG_CHAININFO`), rangos malformados o RVAs nulos. Se preservan los rangos en JSON y el origen se ve en `functions`.

El port solo aplica a PE x86-64 y no implementa las tablas de excepción de ARM/CHPE. Las funciones solo se crean si el inicio cae en código ejecutable decodificado.

## Metadatos x64 `UNWIND_INFO`

Siguiendo `Ghidra/Features/Base/src/main/java/ghidra/app/util/bin/format/pe/PEx64UnwindInfo.java`, se decodifican versión/flags, tamaño del prólogo, registro de marco, slots de `UNWIND_CODE` y RVA del handler cuando existe. Se reconocen los códigos habituales de push, asignación de pila, establecimiento de frame y guardado de registros; de ellos se estima `stack_allocation_bytes` y se exponen los registros guardados junto con las operaciones. El resultado se adjunta a cada función PE x64 y se exporta en JSON; `functions` muestra la asignación estimada cuando se puede calcular.

No se ejecuta el algoritmo de unwinding ni se interpreta el lenguaje de los exception handlers o los payloads de chained unwind. Los códigos desconocidos/insuficientes dejan la estimación de pila como desconocida; la cifra no reemplaza el análisis formal del stack frame de Ghidra.

## Callbacks TLS de PE

El port se basa en `Ghidra/Features/Base/src/main/java/ghidra/app/util/bin/format/pe/TLSDataDirectory.java` y `TLSDirectory.java`. Se toman de LIEF las direcciones de `TLS.callbacks` (con normalización VA/RVA), se limita la lectura a 20 como en Ghidra y se añaden como semillas con nombres `tls_callback_N`; solo se recuperan si caen en instrucciones de secciones ejecutables. `info` y `export-json` exponen la lista.

No se marcan el array de punteros ni `_tls_index`, ni se recrean bookmarks/referencias de datos. La validez final de cada callback depende del filtro de código ejecutable del analizador.

## Llamadas `call` al fall-through

`Ghidra/Features/Base/src/main/java/ghidra/app/plugin/core/function/FunctionAnalyzer.java` omite como inicio de función un destino de llamada que coincide con la instrucción fall-through. El port hace lo mismo para patrones x86 `call $+5` usados para obtener la dirección de retorno en thunks PC-relativos; mantiene el xref de llamada, pero no crea una función ficticia en el byte siguiente.

## Funciones conocidas que no retornan

El siguiente port está basado en `Ghidra/Features/Base/src/main/java/ghidra/app/plugin/core/analysis/NoReturnFunctionAnalyzer.java`, `NonReturningFunctionNames.java` y `Ghidra/Features/Base/data/noReturnFunctionConstraints.xml`. Se incluyen las listas de nombres ELF, PE, Mach-O, Go y Rust de `Ghidra/Features/Base/data/*FunctionsThatDoNotReturn` en `minighidra/data/noreturn/`.

Se reproduce el filtrado por nombre exacto/prefijo con `*`, el descarte de `_` iniciales y la selección de listas por formato. Como MiniGhidraPy no detecta de forma fiable el compilador, añade los nombres Go/Rust a las listas del formato correspondiente; esto puede marcar una coincidencia que Ghidra solo consideraría para ese compilador. Los nombres de símbolos con versión ELF y sufijo `@plt` se normalizan antes de comparar.

Las funciones reconocidas quedan marcadas `no_return`; si una llamada directa o indirecta apunta a una de ellas, el recuperador corta el flujo del llamador en esa instrucción, evitando incorporar el fall-through inalcanzable. La consola lo muestra con `noreturn`. No se portan bookmarks, namespaces, reparación de flujos ni importación de funciones externas.

## Inferencia heurística de no-return

Este incremento traslada un subconjunto de `Ghidra/Features/Base/src/main/java/ghidra/app/plugin/core/analysis/FindNoReturnFunctionsAnalyzer.java`. Se agrupan llamadas por destino y se consideran indicios un inicio de función, una instrucción no decodificada o un trap en la cadena de fall-through. Ghidra comprueba explícitamente `INT3` para x86; este port también trata `ud2` y `hlt` como traps. El recorrido Python está limitado a 256 instrucciones para evitar escaneos descontrolados. De forma predeterminada hacen falta tres sitios de llamada con indicios para marcar el destino; el umbral se puede ajustar con `Analyzer(image, noreturn_evidence_threshold=N)`.

Después, la propiedad se propaga conservadoramente a wrappers cuyos caminos terminales recuperados llaman o saltan únicamente a funciones no-return. La propagación iterativa resuelve cadenas de wrappers y, al finalizar, se reconstruyen los cuerpos una vez para cortar el flujo de sus callers.

No se reproduce el modelo de referencias/listing de Ghidra: la asociación de destinos depende de las referencias que Capstone/LIEF permitan resolver y de los inicios de función ya recuperados. Quedan fuera `callfixup`, referencias inconsistentes a datos/código, bookmarks, creación/reparación de instrucciones y cuerpos exactos del CFG de Ghidra. La prueba de wrappers usa el CFG heurístico de MiniGhidraPy; no debe tomarse como garantía formal de que todos los caminos de ejecución terminan.

## Referencias de operandos escalares

Este port parcial se basa en `Ghidra/Features/Base/src/main/java/ghidra/app/plugin/core/analysis/ScalarOperandAnalyzer.java`. Para formatos no ELF con una base distinta de cero, se consideran referencias escalares los inmediatos no-control-flow que apuntan a una sección mapeada, ignorando valores pequeños y constantes centinela. Se agregan como xrefs `scalar`; también aparecen en el desensamblado y en `export-json`. No se crean funciones a partir de esos datos.

A diferencia de Ghidra, no se consultan relocalizaciones para validar escalares, no se resuelven espacios de direcciones alternativos ni se analizan tablas de salto/subrutinas. Para limitar falsos positivos, los destinos ejecutables solo se conservan si ya son un inicio de función o tienen símbolo; los destinos de secciones no ejecutables se conservan directamente.

## Tablas de punteros y saltos indirectos

Este subconjunto se basa en `OperandReferenceAnalyzer.getAddressTable` y `AddressTable.getEntry`. Si una instrucción referencia una dirección de una sección no ejecutable, se comprueba si allí empieza una secuencia de al menos tres punteros absolutos consecutivos (tamaño 4 u 8 bytes según x86/x86-64) que resuelven a instrucciones decodificadas de secciones ejecutables. Se registran los destinos con xrefs `table`; `tables` y `export-json` muestran las tablas. También se conserva la base de una dirección indexada sin registro base, como `jmp [eax*4 + tabla]`. Si un `jmp` indirecto referencia exactamente una tabla reconocida, sus destinos se enlazan como sucesores del CFG, se marcan con xrefs `switch` y se recuperan esos bloques.

Es una aproximación: solo se examinan direcciones ya referenciadas, se limita cada secuencia a 512 entradas y no se interpretan relocalizaciones, tablas de saltos relativas, entradas con ajustes ni información de tipo. No se enlazan tablas a llamadas indirectas y las referencias a la tabla no crean funciones automáticamente.

## Purga de pila en retornos x86

A partir de `Ghidra/Features/Base/src/main/java/ghidra/app/cmd/function/FunctionPurgeAnalysisCmd.java`, se infiere `stack_purge_size` desde las instrucciones de retorno alcanzables: `ret` equivale a cero y `ret imm16` usa el inmediato. Solo se publica un valor si todos los retornos decodificados coinciden; la consola y `export-json` lo exponen. El valor conserva el indicio directo de limpieza por el callee; por sí solo no determina la convención, aunque el resolvedor ABI posterior lo combina con decoración y evidencia de los callsites.

No se implementa el análisis de referencias a la pila, la creación de stack frame, el modelo de parámetros ni la selección de convenciones near/far de Ghidra. Un valor cero tampoco distingue por sí solo entre cdecl y otras convenciones, y los retornos no recuperados o contradictorios quedan sin valor.

## Recuperación del cuerpo de función

Como referencia de flujo se consultaron `Ghidra/Features/Base/src/main/java/ghidra/app/cmd/function/CreateFunctionCmd.java` y su uso de `FollowFlow`. El análisis Python sigue el flujo condicional/directo interno y el fall-through, se detiene en retornos/saltos terminales y no sigue destinos de llamadas. Evita incluir inicios ya conocidos para reducir solapamientos.

Esto reproduce la idea general de `getFunctionBody`, pero no el modelo de memoria/listing, las referencias indirectas, la resolución de thunks, la reconciliación de cuerpos solapados ni la búsqueda hacia atrás de `findFunctionEntry`.

## Referencias de código

Las firmas viven en `minighidra/function_starts.py`; el análisis no-return en `minighidra/noreturn.py` y `analysis.py`; las tablas/CFG de saltos en `analysis.py`; la resolución de thunks PLT en `image.py` y `analysis.py`; las listas de nombres están en `minighidra/data/noreturn/`. La CLI ofrece `patterns`, `thunks`, `tables` y `noreturn`; `export-json` incluye indicios `no_return_evidence`, tablas y destinos computados.

## Convenciones de llamada y firmas x86/x86-64

El subconjunto ABI está en `minighidra/abi.py` y se conecta al pseudocódigo en `minighidra/decompiler.py`. Se contrastó con los Cspec locales `Ghidra/Processors/x86/data/languages/x86win.cspec`, `x86gcc.cspec`, `x86-64-win.cspec` y `x86-64-gcc.cspec`:

- PE x86 usa por defecto `__stdcall`; ELF/raw x86, `__cdecl`. También se modelan `__fastcall` (ECX, EDX y luego pila), `__thiscall` de Windows (ECX como `this` oculto en la expresión de llamada, pero conservado como primer parámetro formal), y `__regparm1/2/3` de GCC (EAX, EDX, ECX y luego pila). Se reconoce la decoración MSVC habitual y se infieren casos sin decoración con lecturas de registros de entrada, escrituras recientes en los callsites y limpieza observada de pila (`ret imm16` frente a `add/lea esp` o `pop`).
- PE x64 usa el perfil `__fastcall` posicional de Windows: RCX/RDX/R8/R9, alternados por posición con XMM0–XMM3 para argumentos flotantes, shadow space de 32 bytes y argumentos apilados desde el offset 40 relativo al RSP de entrada. Los métodos MSVC decorados pueden usar el mismo perfil con `this` oculto en RCX.
- El Cspec x86-64 GCC de Ghidra llama `__stdcall` a su modelo SysV AMD64: XMM0–XMM7 para valores flotantes, RDI/RSI/RDX/RCX/R8/R9 para enteros, después pila; retornos enteros en RAX/RDX y flotantes en XMM0/XMM1. El perfil Python se etiqueta `sysv_amd64` para distinguirlo del ABI PE.
- Los perfiles describen registros de argumento, pila, retorno, caller-/callee-saved y limpieza. Las llamadas directas consumen el perfil del destino; los argumentos `this` ocultos no se imprimen como argumento explícito. El decompilador conserva las ubicaciones de retorno EAX/EDX:EAX, RAX/RDX, ST0 y XMM0 en las rutas implementadas.

Tras decompilar una función, `Function.calling_convention` y `Function.signature` exponen el modelo inferido; `FunctionSignature` incluye tipo de retorno y parámetros con los tipos heurísticos recuperados del cuerpo. `export-json` serializa esos campos cuando ya se calculó la firma. Los tipos no observables se dejan como enteros del ancho de arquitectura. La eliminación de un retorno escalar para declarar `void` y la inferencia de resultados anchos/vectoriales dependen de evidencia de los callers; con xrefs irresolubles o flujo ambiguo no se descarta el valor observado.

### Motor de tipos/prototipos y ubicaciones ABI (2026-10-22)

La ampliación se basó en el código de tipos y prototipos local, además de los Cspec anteriores:

- `Ghidra/Features/Decompiler/src/decompile/cpp/type.hh` y `type.cc`: clases `Datatype`, `TypeBase`, `TypePointer`, `TypeArray`, `TypeEnum`, `TypeStruct` y `TypeFactory`, con la representación de metatipos, tamaños, campos, offsets y alineación.
- `Ghidra/Features/Decompiler/src/decompile/cpp/fspec.hh` y `fspec.cc`: `ParamEntry`, `ParamListStandard`, `ParamListStandardOut`, `ParamListMerged`, `PrototypePieces`, `ProtoModel`/`ProtoModelMerged` y `FuncProto`. En particular, `join_dual_class`, la regla `hidden_return`, la asignación de `rethidden` y los atributos `dotdotdot`/`firstVarArgSlot` sirven de referencia para la colocación y los prototipos variádicos.
- `Ghidra/Features/Decompiler/src/decompile/cpp/paramid.hh` y `paramid.cc`: referencia para descubrir y puntuar parámetros mediante recorridos de flujo/heritage. El recorrido `ParamMeasure` de entradas y salidas, sus rangos por opcode/slot, el límite de profundidad y la exclusión de backedges en phis se portan al adaptador SSA Python. La asociación de nombres de parámetros de pila y ciertos argumentos/call-spec todavía requiere el grafo reducido; no se porta aquí la recuperación completa de prototipos/`ParamActive` ni el resto de `HighFunction`.

La portación Python se divide entre `minighidra/typesys.py` (`TypeKind`, `CType`, `CField`, `TypeDatabase` y `StorageLocation`) y `minighidra/prototype.py` (`PrototypeResolver`, `PrototypeLayout`). La base registra los tipos escalares C dependientes de x86/PE/ELF, punteros, typedefs, arrays, enums, vectores, structs y unions con layouts y offsets explícitos; admite etiquetas agregadas incompletas para referencias recursivas y tipos de función/punteros a función. El resolvedor mantiene por separado el tipo C y su almacenamiento ABI: piezas de registro con `value_offset`, ubicaciones de pila, paso indirecto y ubicaciones ocultas.

Las reglas trasladadas de los Cspecs cubren:

- **SysV AMD64**: clases INTEGER/SSE/SSEUP recursivas para structs/unions/arrays, unión de clases, rechazo a memoria de miembros desalineados y agregados grandes, reparto independiente de bancos GP/SSE y retorno en RAX/RDX o XMM0/XMM1. Los retornos MEMORY introducen el puntero `sret` en RDI y desplazan los argumentos.
- **Windows x64**: los cuatro grupos posicionales RCX/XMM0–R9/XMM3, shadow space y slots de pila desde RSP+40; agregados que no caben en 1/2/4/8 bytes se pasan indirectamente, y los retornos no elegibles usan puntero oculto. Para `__thiscall`, el `this` marcado `implicit=True` va antes del puntero oculto, tal como `thisbeforeretpointer`; para argumentos variádicos flotantes se modela la copia al GPR paralelo.
- **x86**: pila y registros enteros cdecl/stdcall/fastcall/thiscall/regparm, retorno escalar/EDX:EAX, layouts de agregados de hasta un registro en pentries de registros y los retornos ocultos declarados por los Cspecs GCC. Los argumentos `...` aplican promociones C y se colocan después de los fijos.
- **Variádicas**: `TypeDatabase.promote_vararg` convierte `float` a `double`, aplica promociones enteras y decae arrays a punteros. `PrototypeLayout` puede recibir los tipos concretos de los argumentos variables; en SysV calcula el número de XMM usados para `%al` y en Windows x64 duplica los flotantes en el registro entero posicional correspondiente.

`Analyzer.type_database` permite registrar agregados. `Analyzer.set_prototype(function_o_direccion, FunctionSignature(...))` verifica que los tipos estén definidos, selecciona o recibe el perfil ABI, resuelve y fija (`locked=True`) la firma. Las firmas resueltas incluyen el tipo de retorno/argumentos, piezas de almacenamiento, `variadic`, `hidden_return`, la ubicación de sret, los registros de retorno y el origen del prototipo; `export-json` los serializa. El decompilador honra una firma fijada en la declaración de la función y, en llamadas a destinos con prototipo fijado, ordena los argumentos fijos por las ubicaciones, reconstruye literales compuestos para algunos agregados en registros y no presenta el sret oculto como argumento fuente. Arrays y funciones como parámetros decaen a punteros.

`Analyzer.infer_prototype(function_o_direccion)` expone el siguiente nivel: si no hay una firma fijada, devuelve una firma candidata desbloqueada y anotada con confianza/evidencia; si ya está fijada, la devuelve sin cambios. La implementación etiqueta un parámetro cuando un valor ABI inicial de registro o pila llega, a través de la propagación simbólica, a una lectura de instrucción; por ello no cuenta un registro de argumento que se haya sobrescrito antes de usarse. Las escrituras recientes a registros y las escrituras `push`/stores a slots salientes `[esp/rsp+disp]` en una ventana acotada pueden corroborar callsites. Para los stores se convierte el desplazamiento a coordenadas del SP de la llamada; el recorrido se detiene ante ramas, prólogos de frame o modificaciones del SP no modeladas. Los huecos posicionales anteriores al último índice leído se conservan como placeholders de baja confianza, y reciben confianza moderada solo si se observa que callsites escriben la ubicación correspondiente; esto no prueba que sea un argumento fuente. No se infieren formales nunca leídos fuera de esos huecos. El puntaje describe evidencia de presencia/ubicación, no una probabilidad calibrada ni certeza del tipo C. La puntuación global cae cuando se mezclan bancos GP/SSE SysV porque los registros por sí solos no revelan el orden fuente.

### Medición ParamID y estados de trial

`minighidra/paramid.py` sigue `paramid.hh/.cc` para `ParamMeasure` y `fspec.hh/.cc` para `ParamTrial`/`ParamActive`:

- `PcodeLikeGraph.from_ssa` conserva una operación por `SSAOperation`, enlaza valores por ID, phis, slices y sinks ABI. El suplemento simbólico nombra fuentes de pila y aporta argumentos/call-spec que no están en el p-code SLEIGH sin prototipo.
- El forward walk aplica los roles por opcode/slot de Ghidra, recorre phis fuera de backedges y limita profundidad a diez; el backward walk clasifica valores de retorno. `LOAD`/`STORE` puntúan como lecturas directas, mientras que `INDIRECT` es rank 6. Los userops `ROUND*` mantienen el filtrado por lanes, una extensión para no marcar bytes preservados como argumentos escalares.
- `ParamTrialFlag` usa los bits de `fspec.hh`; se portan las transiciones de banderas, `markUnref`, el killed-by-call heurístico para storage no-stack, el comparator de entrada/grupo/dirección y la comparación por posición fija. `ParamEntry` implementa metadatos de clase, grupos, rangos, alineación, joins, overlaps y slots; `ParamTrialEntry` se conserva como alias de compatibilidad. `StorageLocation.register_offset` conserva subrangos como los lanes SSEUP de `xmm0`, de modo que split/overlap no confundan dos lanes del mismo registro.
- `ParamActive` porta slots y re-registro, solapamiento de rangos, mapeo de slots de CALL con placeholder, contadores/flags de control, sort, `deleteUnusedTrials`, endian-aware shrink, split/join de rangos y renumeración. Se valida el tamaño al unir; split/join se rechazan mientras el placeholder siga sin resolver. `selected` y el índice por nombre son extensiones Python; el indexado `get_trial_for_input_varnode` sigue el ajuste de target/placeholder de Ghidra.
- `analyze(justproto=True, input_names=...)` requiere nombres formales explícitos y mide solo esos storage, incluido sret oculto. `ParamIDAnalysis` construye trials de entrada y `output_active` para registros ABI observados en return-sites; `fillin_param_list(output=True)` ejecuta el fill-in de la lista de salida. No reconstruye el tipo/objeto de retorno completo desde esos registros ni convierte la memoria sret en un trial de salida. Esta resolución no se activa automáticamente en todas las rutas del decompilador.
- El port inicial de `ParamListStandard`/`ParamListStandardOut`/`ParamListRegister`/`ParamListMerged`, asignación/justificación de `ParamEntry`, `buildTrialMap`, reglas y scoring de modelos se añadió en la sección del 2026-10-23 más abajo. Eso no traslada el flujo iterativo completo de `heritage`, todos los veredictos de trials ni todo `FuncProto::resolveModel`; no se afirma paridad total con la recuperación de prototipos ni con el decompilador completo.
- Validación histórica de esta ampliación de ParamID (2026-10-22): suite completa **154/154**, Ruff acotado (`E4,E7,E9,F,I`), `compileall` y `git diff --check`; incluye tests x86/x86-64, lanes SSEUP, flags, slots/placeholders, shrink, split/join, orden y compacción.

El DAG reducido histórico reutiliza expresiones simbólicas y no equivale al p-code de Ghidra: representa un subconjunto de operaciones, cargas/stores y llamadas, y sigue siendo suplemento para ciertos callsites y argumentos de pila. El adaptador SSA primario sí conserva los IDs de todos los `PcodeOp` ya traducidos y los efectos SSA de registro/memoria que produce `SSAHeriage`; no añade guards de aliasing, stack-join, call-spec completo, espacios de memoria por rangos ni tipos de varnode que el SSA actual no modele. El fallback simbólico continúa proyectando al DAG reducido solo sus lecturas/escrituras soportadas. Por tanto, el rank mejora la identificación de fuentes y sus usos, pero no resuelve por sí mismo el orden completo de parámetros, las piezas agregadas ni los prototipos no usados.

Esto **no** porta la máquina completa de Ghidra. El contenedor puede enlazar slots de una firma candidata e incluir placeholders inactivos; no implementa `ParamListStandard.assignMap`, `buildTrialMap`, la agregación de `ParamListMerged`, la correspondencia real con `ParamEntry`, selección/resolución dinámica de modelos, `ProtoModel::resolveModel`, ni el flujo completo de `heritage`/propagación de tipos. Aunque los rangos tienen operaciones split/join/shrink y ordenamiento, no se ejecutan las validaciones de modelo, grupos/exclusiones ni los passes que determinan el veredicto final de cada trial. `used` solo se establece para candidatos activos/seleccionados con storage. No se importan DWARF/PDB, bitfields, metadatos C++ ni layouts de todos los compiladores. La inferencia automática de parámetros y tipos sigue siendo heurística: no recupera formales nunca usados fuera de huecos corroborados, y un binario por sí solo no determina los tipos fuente ni el orden de `...`. En una llamada variádica sin tipos concretos, los argumentos adicionales siguen aproximándose desde registros/escrituras de máquina, y los cuerpos con retornos agregados no siempre se reconstruyen como objetos C aunque el ABI sret sí quede registrado. Es un motor tipado explícito para el subconjunto x86/x86-64 indicado, no paridad íntegra ni una copia de Ghidra.

## Traducción real SLEIGH/p-code por instrucción

`minighidra/sleigh.py` adapta `pypcode` a las instrucciones recuperadas por MiniGhidraPy. La traducción nativa usa los language IDs `x86:LE:32:default` y `x86:LE:64:default`; los `.sla` empaquetados en `minighidra/data/sleigh/` se compilaron desde este checkout de Ghidra 12.3 DEV (`Ghidra/Processors/x86/data/languages/x86.slaspec` y `x86-64.slaspec`) con el compilador local `Ghidra/Features/Decompiler/src/decompile/cpp/sleigh_opt`. Los `.pspec` proceden del mismo directorio y configuran el contexto de la traducción. El pequeño archivo `data/sleigh/README.txt` documenta la regeneración. Se eligió guardar los `.sla` generados (menos de 1 MB en total) para no requerir un compilador C++ ni el árbol Ghidra durante la instalación.

`SleighTranslator.translate_instruction` copia para cada op el opcode SLEIGH, secuencia, dirección, entradas y salida; cada varnode conserva `space`, `offset`, tamaño en bytes y su representación. `SleighInstruction` contiene también longitud real desde `IMARK` y errores localizados. `SleighTranslator.registers` copia los nombres/offsets/tamaños de los alias de registro expuestos por pypcode, sin llamar a `Varnode.getRegisterName()`; el SSA usa esos metadatos para modelar también registros ABI de retorno no nombrados por un op de la función. `SemanticDecompiler.sleigh_instructions` expone las traducciones y `PcodeLikeGraph.instruction_flows` enlaza `sleigh_ops`/`sleigh_error` con cada instrucción. Estos datos no se confunden con los ops del grafo reducido ni detienen la decompilación si una instrucción no puede traducirse. `pypcode` sigue siendo el backend nativo real de SLEIGH; el adaptador, la copia de varnodes y su integración en el analizador son Python.

La traducción se conecta al renderer mediante un intérprete conservador para un subconjunto de p-code entero/booleano y float single/double (incluidos `SQRT`, comparaciones, aritmética básica, truncación y conversiones), registros y aliases de lanes XMM, flags, cargas/stores y ramificaciones internas. `BRANCH`/`CBRANCH` siguen offsets relativos a la operación actual y aceptan el destino `ram` que coincide con el PC siguiente de la instrucción; separan caminos simbólicos con límites de caminos y pasos; se probaron los bucles p-code de `BSF`/`BSR` en x86 y x86-64. Los caminos que no se pueden acotar o requieren opcodes/efectos no representables se rechazan sin aplicar efectos parciales y conservan la ruta `unsupported`; las cargas p-code se capturan en temporales y los stores de memoria se proyectan como escrituras condicionales solo tras completar todas las rutas; también se reconocen los stores por salida directa a varnode RAM, incluidos `LOCK CMPXCHG qword ptr [rip+disp]` y su forwarding/merge posterior. La memoria abstracta de pila conserva stores superpuestos mediante intervalos little-endian y recompone loads parciales y merges de caminos por segmento; para RAM, se reenvían valores por intervalos solo con direcciones absolutas demostrables. Stores por punteros no resueltos invalidan RAM y la pila abstracta por posible aliasing; las llamadas invalidan RAM y los locales cuyo puntero haya escapado. Los userops `LOCK`/`UNLOCK` de las specs locales se preservan alrededor de los RMW atómicos lineales y ramificados probados (`ADD`, `OR`, `CMPXCHG`, `XCHG`); se modelan también `ROUNDPS`/`ROUNDSS`/`ROUNDPD`/`ROUNDSD` para modos inmediatos constantes 0–3. El modo MXCSR (bit 2) y los demás `CALLOTHER` siguen rechazándose. El estado simbólico generado alimenta la propagación y los resúmenes reducidos; por separado, las traducciones SLEIGH completas entran al núcleo SSA y al adaptador primario de `ParamIDAnalysis`. Este pipeline Python sigue siendo parcial frente al SSA/heritage y al recorrido de `ParamIDAnalysis` de Ghidra. El pseudocódigo continúa siendo la salida experimental de `decompiler.py`: se consume semántica real en los subconjuntos implementados, pero no se afirma paridad global.

## Núcleo SSA/heritage p-code en Python (2026-10-22)

La primera implementación independiente del heritage vive en `minighidra/ssa.py`; se integra en `SemanticDecompiler.ssa_function` y se puede obtener sin renderizar C con `Analyzer.ssa(function_o_direccion)`. Se contrastó directamente con el código local de Ghidra:

- `Ghidra/Features/Decompiler/src/decompile/cpp/heritage.cc/.hh`: `buildADT`, `calcMultiequals`, `renameRecurse`, `placeMultiequals` y la secuencia de pases `heritage()`.
- `Ghidra/Features/Decompiler/src/decompile/cpp/block.cc`: construcción de dominadores/árbol de dominadores.
- `Ghidra/Features/Decompiler/src/decompile/cpp/sleigh.cc` y `emulate.cc`: interpretación de destinos `ram` absolutos frente a offsets `const` de ramas p-code relativos a la operación actual.

El port implementa el flujo central de SSA: construye bloques de micro-CFG por secuencias p-code y parte en `BRANCH`/`CBRANCH`/`RETURN`; enlaza los destinos p-code internos y los destinos `ram` recuperados, y trata las llamadas SLEIGH como llamadas que vuelven al caller en vez de saltos intraprocedurales, salvo llamadas conocidas `no-return`; los `call $+5` conservan el push de PC y no reciben clobbers ABI falsos. Calcula RPO, dominadores inmediatos y fronteras; recopila usos/defs, resuelve vivacidad iterativa, coloca `phi` por fronteras iteradas con poda por liveness y renombra siguiendo el árbol de dominadores. Cada byte de registro/varnode se versiona independientemente (los `unique` quedan acotados a su instrucción), por lo que las porciones solapadas de registros participan en el mismo SSA. Las uniones incluyen valores entrantes por arista, incluidos live-ins de las raíces.

La memoria indirecta `LOAD`/`STORE`, los varnodes `ram` directos, las llamadas y los `CALLOTHER` desconocidos actualizan un token SSA global conservador; los RMW de SLEIGH y los stores directos no se omiten. Para las llamadas, el perfil ABI aporta los registros caller-saved y de retorno; se crean definiciones `call_clobber`/`call_return`, se clobberean flags observados y se restablece el valor de SP anterior al `CALL` p-code tras modelar el push del PC de retorno de SLEIGH. `SSAFunction.valid` valida referencias, entradas de phi, snapshots de retorno y dominancia def-use; `complete` registra errores de traducción y ramas p-code internas/dinámicas no resueltas. `return_sites` expone los valores SSA observados en los registros ABI candidatos a retorno en cada `RETURN`. Los registros y temporales son exactos por rango de byte; las lecturas/escrituras de memoria no reciben forwarding de valores desde la memoria SSA.

La implementación no equivale todavía a todo `Heritage`: Ghidra divide el heritage por address space/rangos, refina `Varnode` solapados, aplica guards y pases iterativos específicos para inputs, calls, LOAD/STORE, returns y stack space, y coordina eso con `Funcdata`, tipos y acciones posteriores. Aquí la memoria usa deliberadamente un único token alias-conservador; faltan guards de rango/espacio, stack joins, resolución completa de call-spec/argumentos de pila, refinamiento de aliasing, dead-code/indirect-op passes y propagación de tipos/varnodes de `HighFunction`. `ParamIDAnalysis` ya consume el p-code SSA para registros, operaciones, phis y snapshots de llamadas/retornos, pero el decompiler sigue imprimiendo desde su propagador simbólico previo y conserva el grafo reducido como suplemento. Por ello es progreso validado en los pipelines SSA/ParamID, no paridad total con Ghidra.

Las regresiones cubren diamantes x86/x86-64, poda de merges muertos, ramas internas SLEIGH de `BSF`, loops con valores llevados, alias parcial `AL`, phi de memoria, continuidad/efectos ABI de llamadas directas, snapshots de argumentos de registro en callsites, resultados de llamada que llegan a registros de retorno, snapshots ABI en `RETURN`, `call $+5`, terminación `no-return` y CFG incompleto ante `BRANCHIND` no resuelto. Las 13 regresiones SSA se ejecutan con `python -m unittest discover -s tests -p 'test_ssa.py' -v` desde `mini_ghidra_py/`; la suite completa actual pasó 132/132, junto con `compileall`, Ruff acotado y `git diff --check`. Como referencia histórica, el escaneo de dos PE locales anterior a esta integración encontró `llio_amd64.dll` x64 (222/222 SSA válidas, 212 CFG completos, 60.186 ops) y `WinHelloCPP.exe` x86 (282/282 válidas, 273 CFG completos, 70.547 ops), sin ejecutar los archivos. La validación actual del PE base64 adjunto queda registrada en la sección siguiente.

## Cierre del port de mediciones ParamID (2026-10-22)

## Primer prototipo de pseudocódigo semántico

El prototipo vive en `minighidra/decompiler.py` y se conecta desde `Analyzer.pseudocode`. Se revisaron en este checkout:

- `Ghidra/Features/Decompiler/src/main/java/ghidra/app/decompiler/DecompInterface.java`: el decompilador Java envía la solicitud a un proceso persistente, comprueba el resultado y recibe el árbol/markup y el C. MiniGhidraPy aún no invoca ese proceso: mantiene el requisito de una implementación Python.
- `Ghidra/Features/Decompiler/src/decompile/cpp/coreaction.cc`: `ActionDatabase::universalAction` muestra las fases de heritage, limpieza de código muerto, recuperación de tipos, recuperación de bloques y merges de varnodes.
- `Ghidra/Features/Decompiler/src/decompile/cpp/heritage.cc` y `op.hh`: referencia del modelo de variables/p-code SSA y de los merges de valores en uniones del CFG.
- `Ghidra/Features/Decompiler/src/decompile/cpp/blockaction.cc` / `blockaction.hh`: `ActionBlockStructure`, `CollapseStructure::ruleBlockIf`/`ruleBlockIfElse`, `ruleBlockWhileDo`/`ruleBlockDoWhile` y clases de bloques estructurados (`BlockIf`, `BlockIfElse`, `BlockWhileDo`, etc.); se usan como referencia de un primer pase conservador, no como port completo de `CollapseStructure`.
- `Ghidra/Features/Decompiler/src/decompile/cpp/opcodes.hh` y `printc.cc`: referencia para operadores enteros y su impresión como expresiones C.

La implementación Python vuelve a decodificar cada instrucción con Capstone en detalle y traduce un subconjunto explícito a expresiones simbólicas. Propaga registros de propósito general, MMX de 64 bits, XMM de 128 bits, pila y una pila x87 abstracta por el CFG; crea `phi(...)` en uniones y pliega constantes. Modela, entre otras, operaciones aritméticas/lógicas, flags y condiciones comunes, `ADC`/`SBB`, `MUL`/`IMUL`/`DIV`/`IDIV` implícitos, transferencias x87 de comparación a `SAHF`, movimientos x87; un subconjunto MMX; y movimientos SSE, operaciones empaquetadas de enteros (`PUNPCKLDQ`, `PSHUFD`, `PCMPEQD`, `PMINSD`/`PMAXSD`, shifts y lógica) y conversiones/operaciones escalares SSE de punto flotante. También modela `MOVS`/`STOS`/`LODS`/`CMPS`/`SCAS` con prefijos `REP*`, el contador y los punteros, y el sentido conocido de DF; si el resultado de un bucle de comparación depende de datos desconocidos, lo conserva simbólico. `CPUID` deja sus salidas desconocidas en vez de reutilizar valores obsoletos. En x86/x86-64 aplica perfiles ABI parciales de `abi.py` para localizar parámetros, retornos y registros volátiles/preservados; en x86 también recupera los slots de pila relativos a la entrada y los argumentos apilados recientes. La selección de convención y el cálculo de aridad siguen siendo heurísticos, tal como se detalla en la sección ABI. La eliminación experimental de un retorno `EAX`/`RAX` para declarar `void` solo se aplica cuando los sitios de llamada recuperados comprueban que se sobrescribe antes de leerse; una lectura previa cuenta como retorno usado. Si hay xrefs irresolubles o flujo ambiguo, no se descarta el valor observado. En PE x64, los cuatro slots de home/shadow space (`[rsp+8]` a `[rsp+0x20]` relativos al RSP de entrada) se nombran `home_slot_1` a `home_slot_4`, no como parámetros formales; los argumentos realmente pasados en pila empiezan en `param_5`. Los `call $+5` se modelan como captura de la dirección de retorno; un `jmp` terminal a otra función ya recuperada se representa como tail-call con prototipo/argumentos desconocidos. Después de estas rutas especializadas, un intérprete simbólico consume para otras instrucciones las secuencias SLEIGH compatibles: ops enteros/booleanos y un subconjunto `FLOAT_*` de 32/64 bits (comparaciones, aritmética básica, raíz cuadrada, truncación y conversiones), registros generales, XMM y sus aliases de lanes, temporales `unique` con subrangos solapados, flags, `LOAD`/`STORE`, varnodes RAM absolutos y ramificaciones internas acotadas. En `CALLOTHER`, preserva los marcadores locales `LOCK`/`UNLOCK` y reconoce los ids empaquetados `0xE7`–`0xEA` para `ROUNDPS`/`ROUNDSS`/`ROUNDPD`/`ROUNDSD`, con control inmediato constante distinto de MXCSR; estos ids no se generalizan a otros lenguajes o assets. El fallback conserva temporales p-code por instrucción y resuelve varnodes `unique` con subrangos solapados, además de respetar alias de registros y proyecta accesos a pila en el estado simbólico, conservando stores superpuestos por bytes y recomponiendo lecturas parciales; la memoria RAM conocida solo persiste para intervalos absolutos y se invalida ante aliasing potencial; el análisis de caminos internos implementado cubre `BSF`/`BSR`, operaciones y selecciones float escalares como `MINSS` (con branch al fin de instrucción), captura cargas en temporales y proyecta stores de memoria como escrituras condicionales en secuencias ramificadas. Los demás opcodes o semánticas no soportadas permanecen en la frontera explícita `unsupported`.

Para las instrucciones x86 se contrastó la semántica Python con `Ghidra/Processors/x86/data/languages/ia.sinc` y `lockable.sinc`: allí `CPUID` advierte explícitamente que los valores no son correctos y expone sus efectos; las construcciones `lockx`/`unlock` delimitan los userops `LOCK()`/`UNLOCK()`; las macros `rep`/`repe`/`repne` definen el manejo de CX/ECX/RCX, y las reglas de `MOVS*`, `CMPS*`, `SCAS*`, `MOVD`, `MOVQ`, `PUNPCKLDQ`, MMX y SSE (incluidas conversiones escalares) muestran los resultados trasladados a registros/memoria. Para contrastar ABI se revisaron `Ghidra/Processors/x86/data/languages/x86win.cspec`, `x86gcc.cspec` y `x86-64-win.cspec`, que describen ubicaciones de parámetros, registros de retorno y limpieza de pila para modelos concretos. El levantamiento simbólico que imprime el pseudocódigo conserva reglas Python explícitas para una parte de ese repertorio; no debe confundirse con el traductor SLEIGH por instrucción ni con un clasificador completo de prototipos.

El paralelismo con Ghidra es arquitectónico, no una copia del algoritmo: el p-code SLEIGH real se genera por instrucción con pypcode, `ParamIDAnalysis` recorre el adaptador de todas las operaciones de la SSA construida y el fallback del renderer consume un subconjunto de ops enteros, flags, memoria y ramificaciones acotadas. El grafo reducido sigue aportando suplementos para callsites/stack, pero la inferencia ParamID ya no se limita a ese DAG. Flags o efectos que no se puedan determinar quedan simbólicos; salvo los bucles internos de `BSF`/`BSR`, el store condicional de `CMPXCHG` y los marcadores `LOCK`/`UNLOCK` para RMW p-code validados, las demás ramificaciones internas p-code, el aliasing general y SSA de memoria (solo se reenvían intervalos de pila y RAM absoluta con invalidación conservadora), AVX/YMM solo parcial y numerosas instrucciones/estados de máquina aún no se modelan. Aunque se añadieron los casos implícitos `MUL`/`IMUL`/`DIV`/`IDIV`, las formas y tamaños no cubiertos se conservan como aproximaciones o valores desconocidos. Los merges que el pase no puede materializar siguen apareciendo como expresiones `phi(...)` aproximadas, no como variables high-level equivalentes a `HighVariable` de Ghidra; tampoco se recuperan tipos, prototipos, estructuras, variables globales ni nombres equivalentes a `HighFunction`. Hay un pase inicial de estructuración de condiciones sencillas y un caso acotado de `do/while` de un solo bloque, pero no se estructuran loops generales ni se implementa el algoritmo completo de `CollapseStructure`. Por ello el resultado es experimental y no promete pseudocódigo idéntico ni semántica completa para binarios arbitrarios.

### Estructuración conservadora de flujo de control

Las referencias principales son `CollapseStructure::ruleBlockIfElse` y `ruleBlockDoWhile` en `Ghidra/Features/Decompiler/src/decompile/cpp/blockaction.cc`. Para `if`/`if-else`, Ghidra exige una condición binaria, salidas de decisión no marcadas como `goto`, brazos con entrada única y una salida cada uno, y un destino común; `ruleBlockIf` aporta el caso de una cláusula con salida al bloque que sigue. El pase Python en `_structure_control_flow` aplica un subconjunto conservador: ramas directas a bloques recuperados, brazos privados de un bloque y un join verificable, o dos ramas privadas terminales de retorno/trap/no-return.

Para `do/while`, solo reconoce una basic block condicional con una arista a sí misma y una salida local hacia delante, un máximo de un predecesor de entrada adicional y sin `goto` incrustado en las sentencias del cuerpo. Mueve las sentencias anteriores a la condición a `do { ... } while (...)`; los `phi` de loop se conservan como expresiones internas y no se convierten en variables de iteración. No está portado `ruleBlockWhileDo` (cabecera y cuerpo separados). Los bucles multi-bloque, `break`/`continue`, switch/saltos calculados, brazos compartidos, regiones irreducibles y aristas ambiguas conservan el etiquetado y los `goto` previos.

En un diamante con dos predecesores exactos, el pase asocia las entradas `phi` con el orden de predecesores, las convierte en asignaciones a la variable de merge dentro del `if`/`else` y elimina el `phi(...)` del join. ### Diferencias y límites verificables

- La cobertura Cspec se ha validado contra los cuatro archivos x86 indicados; no es un decoder general de todo `fspec` ni de cada formato/arquitectura Cspec. Reglas XML desconocidas quedan visibles en `unsupported_rules`, en vez de darse por implementadas.
- `PrimitiveExtractor` está portado sobre el subconjunto de `CType`: expande primitivas, arrays y estructuras, calcula refinamientos comunes de unions y conserva `getSize`/`getAlignSize` para tipos agregados; informa de elementos unknown, desalineación y holes. `join_dual_class` clasifica primitivas por tile, consume recursos en una copia del estado y hace spill opcional a stack; la justificación/endian-aware de las piezas sigue `justifyPieces`. Las ubicaciones Python registran `value_offset` en orden lógico y no construyen el `JoinRecord` interno de `Architecture::joinPieces`. La elegibilidad dual replica el chequeo C++ de extracción válida, lista no vacía y ausencia de holes; los flags unknown/aligned se conservan, pero no se rechazan por sí solos en `MultiSlotDualAssign`. `constructFloatExtensionAddress` ahora crea un `JoinRecord` de una pieza física con tamaño lógico menor, y `get_equivalent_piece` mapea offsets join-space a la pieza real; el parser Cspec también conserva `extension="float"`. No se asigna un offset de join-space del `Architecture` ni se portan los pases `Heritage::floatExtensionRead/Write` que materializan `FLOAT_FLOAT2FLOAT`. Sigue sin cubrir todo el universo de metatipos/layouts de Ghidra ni validar las precondiciones de cada acción al decodificar el Cspec.
- `GotoStack`, `ConvertToPointer` y `HiddenReturnAssign` se portan para los modelos locales; `HiddenReturnAssign` reconoce `strategy="normalparam"`/`"special"` y `voidlock`. No están implementadas todas las demás acciones, modificadores y callbacks de usuario, los efectos variádicos ni todos los efectos diferidos (`autoKilledByCall`) de los modelos C++.
- `ParamListMerged` conserva la unión de recursos para consulta y selecciona un modelo concreto por scoring; no es una implementación completa de todos los flujos de `FuncProto::resolveModel` ni de los estados parciales del decompilador.
- La integración ParamID rellena listas de entrada y de salida: `output_active` se construye con los registros ABI observados en return-sites y `fillin_param_list(output=True)` ejecuta `ParamListStandardOut`. Esto no reconstruye el tipo agregado de retorno a partir de registros ni crea un trial de salida para la memoria sret; una firma tipada fijada sí resuelve esos casos mediante `PrototypeModel.assign_signature`. No se portan aquí los pases posteriores que deciden definitivamente el veredicto de todos los trials, la recuperación de tipos desde DWARF/PDB ni el resto del pipeline `Action` de Ghidra.
